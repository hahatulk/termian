# AGENTS.md — правила работы с Termian

Этот файл предназначен для ИИ-агентов, инструментов автоматизации и разработчиков, меняющих репозиторий. **Прочитайте его и относящиеся к задаче README до любых правок.** Если появится `spec.md` или локальный `AGENTS.md` в затрагиваемом каталоге, сначала прочитайте их и соблюдайте более конкретные правила. Не обходите ограничения без явного запроса пользователя.

## Клиенты: нативный (корень) и legacy (Tauri)

Идёт переход интерфейса с WebView на нативный Rust UI (GPUI), см. [ADR 0001](docs/adr/0001-native-gpui-client.md).

- **Нативный клиент** — корневые `Cargo.toml` и `src/`. Новый функционал и перенос экранов делаются здесь. Логику, которую можно тестировать без окна, держите в библиотеке (`src/lib.rs` и модули), а `src/main.rs` — только окна и отрисовка.
- **Legacy-клиент** — `legacy/` (бывший `tauri/`): Tauri + WebView. Он остаётся релизным, пока нативный клиент не достигнет паритета; поддерживайте его в рабочем состоянии, но новых крупных функций туда не добавляйте. Внутри `legacy/` действуют прежние правила: исходники только в `legacy/src/` (`rust/` — нативный Rust, `ui/` — интерфейс, `bridge/` — мост), не создавайте `src-tauri/`, `ui-src/` или копии `src/`.
- Electron удалён: не восстанавливайте его. Не создавайте третьих клиентов и дополнительных деревьев приложений.
- `cloud-sync-server/` — **самостоятельный сервер синхронизации**, а не desktop-клиент.
- В legacy-UI и названиях функций могут оставаться исторические ссылки на Electron или совместимые API. **Не удаляйте работающий код по одному имени или комментарию**: он может обеспечивать Tauri-мост.

## README и документация — обязательная часть изменений

Используйте рекомендации GitHub по структуре README:
[About the repository README file](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-readmes).

1. **`README.md` в корне — GitHub-витрина проекта:** назначение и преимущества, возможности, быстрый старт, поддерживаемые платформы, сборка, помощь и ссылки на подробные инструкции. Пишите кратко и по делу; длинные технические детали выносите в профильные README.
2. **`legacy/README.md` — техническая документация клиента:** окна, архитектура, SSH, синхронизация, команды, релизы, известные ограничения и сохранность данных.
3. **`legacy/src/ui/README.md` — особенности интерфейса:** точки входа, известные ограничения, команды проверки и аккуратное редактирование бандлов.
4. **`cloud-sync-server/README.md` — запуск, API, Docker и безопасность сервера.**
5. Используйте **GitHub Flavored Markdown**, понятные заголовки, кодовые блоки с языком, небольшие таблицы и **относительные ссылки** для внутренних файлов и каталогов. Не вставляйте мёртвые пути, выдуманные команды, неподтверждённые платформы или значки «готово» без проверки.
6. **Обновляйте документацию вместе с изменениями** интерфейса, поведения, форматов данных, команд сборки, структуры папок, CI, требований к секретам или платформам. Если поведение ещё не проверено, прямо отмечайте это.
7. **Не рекламируйте Electron как доступный клиент.** Не добавляйте в README ссылки на удалённый каталог `electron/`. Историческое происхождение UI можно упоминать только для технического контекста.

## Сборка и тестирование

Из корня репозитория:

```bash
npm test                  # cargo test нативного клиента
npm run dev               # запуск нативного клиента
npm run legacy:install    # npm ci в legacy/
npm run legacy:test
npm run legacy:check:web
npm run legacy:build:mac
npm run legacy:build:windows
```

Те же команды legacy можно запускать напрямую в **`legacy/`**:

```bash
npm ci
npm test
npm run check:web
npm run dev
```

Production на соответствующей ОС:

```bash
npm run build:windows
npm run build:mac
```

- Для нативного клиента выполняйте `cargo test` в корне. Для изменения JS/UI legacy как минимум выполняйте `npm test` и `npm run check:web`. Для Rust дополнительно проверяйте Cargo-компиляцию/тесты там, где возможно. Не утверждайте, что GUI проверен, если не запускали его.
- `.github/workflows/release.yml` собирает только Tauri Windows x64 и macOS Apple Silicon ARM64; Android-клиент и APK не поддерживаются. Не публикуйте неполный релиз. На macOS подписывайте ARM64 .app (ad-hoc - без Apple Developer, Developer ID + notarization для доверенного распространения), проверяйте codesign, а для Developer ID дополнительно spctl.
- Релиз обязан содержать подписанные пакеты автообновления (`*.app.tar.gz`, portable `*-win-x64.exe` и установщик `*-win-x64-setup.exe` + `.sig`) и `latest.json` с ключами `darwin-aarch64`, `windows-x86_64`, `windows-x86_64-nsis`. Портативную копию Windows публикуйте до NSIS-упаковки (упаковщик помечает бинарник типом сборки). Не меняйте `plugins.updater.pubkey` в `legacy/src/tauri.conf.json` без ротации ключа: установленные копии принимают только подписи текущего ключа. Не добавляйте webview права `updater:*`.
- Релизные файлы и промежуточная компиляция находятся в `legacy/dist/`. Не создавайте дополнительные деревья приложений ради сборки.
- `legacy/dist/.cargo/` и `legacy/dist/web/` — воспроизводимые результаты сборки. **Никогда не очищайте весь `dist/` целиком**, поскольку рядом может находиться пользовательский профиль и готовые файлы.
- **Не уничтожайте Rust-кэш автоматически после release-сборки.** `publish-windows.mjs` и `publish-mac.mjs` по умолчанию сохраняют `dist/.cargo/` для инкрементальной компиляции и post-job `rust-cache`. GitHub Actions обязан кэшировать именно `legacy/src -> ../dist/.cargo`, а Rust-тесты выполнять `cargo test --release --lib`, без второй debug-компиляции. На macOS обязательно запускайте Cargo-тесты с `--target aarch64-apple-darwin` и тем же `MACOSX_DEPLOYMENT_TARGET=11.0`, что у DMG, иначе компиляция повторяется для другого target. Очистка допустима только явно: `npm run clean:rust-cache` или `TERMIAN_CLEAN_BUILD_CACHE=1`; это не должно затрагивать `termian-data/`.
- Документационные изменения сами по себе не требуют тяжёлой production-пересборки. Выполняйте сборку при изменении исходников или по явному запросу.

## Данные и безопасность

- **Сохраняйте `legacy/dist/termian-data/`**, Vault, WebView2-профили, конфиги собственного облака, снимки и резервные копии.
- Не удаляйте Docker volume `sync-data` и не выполняйте `docker compose down -v` без явного запроса и подтверждённого плана восстановления.
- Не выводите в логи и не добавляйте в Git токены, пароли, приватные ключи, файлы `.env`, локальные профили или содержимое зашифрованных снимков.
- Синхронизация — **трёхстороннее слияние** (`legacy/src/bridge/sync-merge.js`): изменения разных записей объединяются, одна и та же запись, изменённая на обеих сторонах, — конфликт, который **никогда не разрешается автоматически** (только выбором пользователя). Ежечасная автосинхронизация отключается в настройках. Сохраняйте меры безопасности: условную отправку (`If-Match`), резервную копию перед импортом, отказ от удаления всех данных при пропавшем снимке на сервере. «Отправить» и «Получить» по-прежнему заменяют снимок целиком.
- При исправлении UI сохраняйте рабочие SSH/SFTP, Vault, настройки и доступность технических ошибок подключения. Сначала добавляйте или уточняйте тесты, потом меняйте код.
- **Первый запуск без данных не должен оставлять чёрный экран.** `src/bridge/startup-recovery.js` устанавливается только в главном (`type=ui`) окне: кратко показывает состояние запуска, отслеживает реально отрисованный React UI, допускает не более одной автоматической перезагрузки WebView через `sessionStorage` и затем предлагает ручное повторение. Не выполняйте для этой ситуации удаление `termian-data/`, IndexedDB или сброс Vault. Изменения проверяйте тестами `tests/first-launch.test.mjs` и, если возможно, изолированной новой копией EXE с **отдельным** тестовым WebView2-профилем, не трогая рабочий.

## Перед завершением задачи

- Убедитесь, что ссылки и команды в README соответствуют реальному дереву и `package.json`.
- Проверьте, что не добавлена новая копия Electron, `src-tauri/` или тяжёлые временные артефакты.
- Проверьте состояние Git; **не коммитьте, не пушьте и не переписывайте пользовательские изменения без явного запроса**.
- Укажите, какие файлы обновлены, что проверено и какие ограничения остались. Не выдавайте настройку CI за подтверждённый успешный релиз.
