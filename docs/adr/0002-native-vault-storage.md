# 0002. Собственное хранилище Vault нативного клиента

- Статус: принято
- Дата: 2026-11-13

## Контекст

Нативный клиент читал хосты из профиля legacy-клиента (WebKit IndexedDB, записи SerializedScriptValue, поля зашифрованы `localKey` из keychain) и ничего туда не писал. Для экрана NEW HOST и правки хостов нужно место, куда записывать изменения.

Запись прямо в IndexedDB legacy-клиента потребовала бы точно воспроизвести формат WebKit и шифрование, а при одновременной работе двух клиентов грозила бы конфликтами и порчей Vault.

## Решение

У нативного клиента своё хранилище — один файл `vault.bin` в каталоге данных `termian-native` (на macOS `~/Library/Application Support/termian-native/`):

- формат: заголовок `TMNVLT1\n`, 24-байтный nonce и XSalsa20-Poly1305 поверх JSON с содержимым Vault;
- 32-байтный ключ хранится в системном хранилище секретов (служба `termian-native`, запись `vault-key`) и создаётся при первом сохранении;
- если файла ещё нет, Vault один раз импортируется из профиля legacy-клиента; профиль legacy при этом не меняется;
- запись атомарная: сначала временный файл рядом, затем переименование.

В режиме `TERMIAN_DEMO` хранилище — отдельный файл `termian-native-demo/vault.bin` во временном каталоге с фиксированным тестовым ключом, без обращения к keychain.

## Последствия

- Правки в нативном клиенте не видны legacy-клиенту и наоборот: после первого импорта данные расходятся, пока оба клиента не подключены к одному своему облаку (портативный снимок `termius-portable-snapshot` у них общий).
- Пароли и ключи из legacy при импорте по-прежнему не расшифровываются; пароли, введённые в нативном клиенте, хранятся только в зашифрованном `vault.bin`.
- Синхронизация с собственным сервером должна будет работать с этим хранилищем.
